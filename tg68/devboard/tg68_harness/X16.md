# x12 vs x16 master clock: evaluation on the dev-board harness

The question: would running the TG68 build from a 16x master clock
(ICS570B S0 grounded, 16 x 7.09 MHz = 113.5 MHz) instead of today's 12x
(85.1 MHz) make it faster? Measured 2026-11-06 on an iCESugar-Pro v1.3, no
Base64 hardware involved. On the harness, 7M is 7.143 MHz in both
modes (85.714 / 12 and 114.286 / 16), so only the master clock differs.

## Summary

- **About 16% faster** for everything that runs from the caches or fast
  RAM, and 8% for Chip RAM reads. Measured on hardware and matched by
  simulation to the microsecond.
- It is not 33% because the TG68 kernel's internal paths need about 41 ns.
  At 85.7 MHz that is STEP 4 (46.7 ns); at 114.3 MHz it has to be STEP 5
  (43.8 ns). The kernel step itself only gets 6% shorter. The rest of the
  gain comes from the adapter, caches and SDRAM, whose costs are counted
  in clocks.
- **Timing is not met at 16x.** 760 single-clock paths miss the 8.75 ns
  period, by up to about 2 ns (worst classes below). The kernel's 5-clock
  paths pass with 2.15 ns to spare. The harness build still passed the
  full test on one board at room temperature, but that is luck, not margin.
  The single-clock paths have to be restructured before x16 is safe in an
  A500.
- **The SDRAM is fine at 114 MHz, CL2.** The soak test with tRCD/tRP 3 and
  tRC 7 clocks ran 89 full 32 MB passes with 0 errors
  (`../sdram_test/build.sh bit114`).

## Speed: hardware, full test program (`build.py sw`)

| caches on | x12 85.7 MHz | x16 114.3 MHz | gain |
| --- | --- | --- | --- |
| fast RAM write 64 KB | 12263 us | 10519 us | 1.17x |
| fast RAM read 64 KB | 12328 us | 10447 us | 1.18x |
| fast RAM copy 64 KB | 20586 us | 17683 us | 1.16x |
| CRC32 4 KB (CPU) | 39907 us | 34349 us | 1.16x |
| sieve to 8192 (CPU) | 33588 us | 29019 us | 1.16x |
| Chip RAM read 4 KB (7M bus) | 2011 us | 1867 us | 1.08x |
| memtest 15 MB random | 12233 ms | 10544 ms | 1.16x |

With the caches off the gain is slightly larger: 1.19-1.21x on fast RAM
and the CPU-bound tests, 1.07x on Chip RAM.

## Timing: harness x16 build, check_timing at 114.29 MHz, STEP 5, SETTLE 4

| class (1T = 8.75 ns) | worst | slack | failing |
| --- | --- | --- | --- |
| adapter ctrl -> logic | 10.84 ns | -2.09 | 147 |
| clkena -> kernel | 10.29 ns | -1.96 | 113 |
| logic -> kernel | 10.46 ns | -1.71 | 6 |
| icache/direct -> logic | 10.23 ns | -1.48 | 34 |
| adapter ctrl -> read-data latch | 10.06 ns | -1.31 | 14 |
| logic -> logic | 13.75 ns | -5.00 | 447 (mostly the harness-only /HALT synchroniser paths, see README) |
| kernel -> kernel (5T) | 41.60 ns | +2.15 | 0 |

The released step 4 routing, re-checked at 113.5 MHz with STEP 5, gives the
same picture: −2.4 ns on cache/direct → logic and −2.2 ns on clkena → kernel
(fan-out to ~1100 kernel flip-flops).

## What x16 would take

1. **The single-clock paths.** These are the patterns that worked before
   (tg68/CLAUDE.md rule 3):
   - Replicate `k_clkena`, so no copy drives 1100 flip-flops.
   - Register the cache-hit decode one clock earlier.
   - Move work one clock later from latched registers.
   Each added clock costs 8.75 ns, so even a cache hit that grows from 7 to
   8 clocks (70 ns) is still faster than today's 7 clocks at 12x (82 ns).
2. **Parameters**, already in `base64_tg68_top`. The defaults reproduce the
   step 4 bitstream bit for bit. The harness's x16 set:
   - `CLK_MULT 16`, `CLK_HZ`, `CPU_MULT 8`, `TG_STEP 5`, `TG_SETTLE 4`;
   - SDRAM `SD_TRCD 3`, `SD_TRP 3`, `SD_TRFC 7`, CL2.
3. **The Base64 itself, not tried here.**
   - `DTACK_LAT` (and possibly `PHASE_OFS`) has to be recalibrated on a real
     motherboard. The 12x value 4 is 2 synchroniser clocks plus the 35 ns AS
     output delay as 3 clocks. At 8.75 ns that delay is 4 clocks, so expect
     about 6, which is the stated limit before the S6 tick.
   - Check the ICS570B S0/S1 table in the datasheet before grounding pin 6.

Reproduce:
```
python3 build.py sim --x16                    # functional, SDRAM model timing-checked
YOSYS=yowasp-yosys NEXTPNR=yowasp-nextpnr-ecp5 python3 build.py bit --x16
python3 host/run.py build/test.bin --bit build/tg68_harness_x16.bit --port ...
```
